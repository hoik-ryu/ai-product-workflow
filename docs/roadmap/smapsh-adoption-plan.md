# SMAPSH(badminton-playbook) `/product-build` 적용 계획 (초안, 2026-11-12)

상태: **계획만 작성.** 원본 저장소는 읽기 전용으로 조사했습니다. 엔진 설치, 파일 수정, 원장 생성, 기존 구현 등록, 승인 변경은 하지 않았습니다. 아래 단계는 모두 사용자 승인 후에만 실행합니다.

## 2. 전제 조건(적용 전에 반드시)

1. **다른 세션의 작업 정리**: I3 진행 세션이 멈춘 시점에, 사용자가 SMAPSH의 현재 구현을 **커밋**합니다.
   - 커밋 전에는 시작하지 않습니다. 대량의 미커밋 변경 위에서 시작하면 모든 수정이 `uncommitted_in_scope`·`base_conflict`가 되고, 다른 세션 작업과 구분할 수 없습니다.
2. **결정 확인**: 이 문서 §6의 사용자 결정(P7·Q5·P2와 차단 분류)을 받습니다.
3. **사전 기록**: 적용 직전 원본의 `.ai-workflow/`·`docs/` 해시와 `git status`를 기록합니다. 롤백과 사후 비교에 씁니다.

## 4. 기존 구현을 AC·테스트에 연결하는 절차

1. **태그 형식**: 프로필 `tag_style = ["prefix", "pytest_name"]`
   - 프런트: `SCR-212 / AC-010 / AC-016: …`
   - 백엔드: `test_ac_010_…`
   - 복제본에서 Must AC 100개 중 57개가 태그된 통과 테스트(E2 후보)로 확인됐습니다.
2. **`verify` 결과**: 배치별 AC 판정이 나옵니다. 2026-11-12 복제본 기준 명단 배치는 다음과 같습니다.
   - AC-010·100: E2
   - AC-013·066: E2(목표 E3, 기존 구현)
   - AC-014·018·097·105·106·107: 태그 테스트 없음
3. **untested AC**는 원장의 `evidence_gap`(비차단)으로 남깁니다. 테스트를 보강할 배치를 따로 계획하거나, `batch-start`로 테스트 작업을 추가합니다. 예: AC-014·105–107은 테스트 주석에 `AC-013·014·105–107` 축약 표기만 있으므로 태그를 붙이면 E2 후보가 됩니다.
4. **목표 E3 AC**(보안·권한·데이터 손실)는 기존 구현이라 실패 우선 기록이 없습니다. AC마다 사용자에게 다음 중 하나를 받습니다.
   - (a) 목표 E2로 변경(사유 기록)
   - (b) 결함 주입 증거 인정
   - (c) 다음 수정 때 실제 실패→수정 기록
   - 목표를 자동으로 낮추지 않습니다.

## 6. 정책 검토(P7·Q5·P2) — 사용자 결정 대상, 원장에 결정으로 기록하지 않음

### P7 — 같은 4명·같은 팀 구성을 피할 수 없을 때

- **원문**(b3:17): "끝까지 못 찾으면 그 대진을 그대로 둠 — 서버 구현 시 거부·오류 처리 결정 필요". I3 문서 U7(i3:116)이 같은 공백입니다.
- **승인 명세**
  - C-05: "항상 금지"
  - **NFR-003**: "0건이어야 합니다. **가능한 조합이 모두 소진된 경우만 예외이며, 이때는 FR-013으로 표시합니다.**"
  - FR-013(Should): 완화 표시
- **현재 구현**
  - `lineup.ts`·`schedule.ts`는 1e12 벌점만 주고 통과시킵니다. 완화 표시 종류(`Relaxation`)에 '같은 4명'이 없어 **아무 표시 없이 위반합니다**(NFR-003의 '표시' 위반).
  - 복제본 실측: 개인전 4명·6경기에서 같은 구성 3회.
  - 서버 생성은 아직 없습니다(I3-b·I4에서 이식 예정, 골든 JSON 동등성).
- **기존 오류 계약**
  - `{"error": {code, message, details}}`, snake_case
  - 409는 상태·버전 충돌
  - 422는 '입력으로 만들 수 없음'(`min_players`, `unscored_players`, `invalid_score`, `not_eligible`)
- **추천(결정 아님)**: **허용 + 표시**(NFR-003 그대로)
  - 생성은 성공(200/201)으로 둡니다. 해당 경기 `relaxations`에 새 값(예: `same_matchup`)을 넣고, UXD-007 배지('같은 구성 반복' 등 문구 필요)로 표시합니다.
  - 오류 코드는 필요 없습니다.
  - 거부안(422 `lineup_unavoidable_repeat`)은 NFR-003과 맞지 않고, 소수 인원 운영을 막습니다.
- **필요한 일**
  - 배지 문구 결정(UX 문구 = 문서 반영 제안)
  - 세션·청백전 공통 적용(C-19)
  - 골든 테스트에 '불가피' 사례 추가
- **차단 유지**: 서버 생성 이식 배치(I3-b·I4)에 한해 유지를 권장합니다. 이식하면서 조용한 위반이 그대로 복사되기 때문입니다. 이미 구현된 Mock UI 배치는 차단하지 않습니다.

### Q5(B4) — 교체 후 경기 수 차이

- **원문**(b4:15): "교체 후 차이가 2 이상이면 확인 창으로 경고하고 운영진이 허용 가능(차단하지 않음)"
- **승인 명세**
  - C-14: "차이 최대 1은 **자동 생성과 다시 생성에서 보장**하고, 이후 **수동 교체로 2 이상이 되면 경고만** 합니다."
  - **AC-079**: "경고가 보이지만 교체는 반영됩니다."
- **현재 동작**
  - 교체: 경고 후 허용으로 명세와 일치합니다. 차이는 '확인 창으로 묻고 반영'하는 표현 방식뿐입니다(④·⑤ 수준).
  - 자동 생성(복제본 실측)
    - 개인전: 차이 ≤1 보장(14명·10경기 2–3경기, 20명·20경기 4경기)
    - 팀전 청·백 인원이 같을 때: 차이 0
    - **팀전 인원이 다를 때**(청3·백5 10경기 → 4–7경기, 차이 3 / 청2·백6 6경기 → 차이 4): 각 팀 안에서는 고르지만, 전체 기준 '선수 간 차이 최대 1'은 원리상 불가능합니다(경기마다 각 팀 2명).
- **규칙을 만족하지 못하는 입력**
  - 팀전에서 청·백 인원이 다른 경우
  - (C-05와 겹쳐) 극소수 인원
- **추천(결정 아님)**
  - **교체 경고 동작은 유지**합니다(명세 일치). Q5는 비차단으로 재분류하고, 확인 창 표현은 기록만 합니다.
  - **팀전 불균등 인원의 C-14 해석**은 사용자가 결정합니다.
    - 권장: "팀전은 팀 안에서 차이 최대 1"로 명세를 보완하고, 경기 수 분포 미리보기(UXD-071)에 팀별 분포를 표시합니다. 알고리즘은 바꾸지 않습니다.
    - 대안: 인원 차이가 있으면 생성 전 경고(알고리즘·화면 수정)
  - 이 결정은 I3-b 서버 이식 전에 필요합니다.

### P2 — 레벨별 방식과 성별 조합의 관계

- **원문**(b3:12): "✅ 방향 결정(사용자 지시 2026-11-11, B4 요청) … 성별 조합 제약을 먼저 맞추고, 그 안에서 레벨(점수 구간)·실력 밸런스를 최적화 … 승인 명세 C-01·C-03 문구 보완은 기획 개정 시 반영 필요"
