# M3 Design-to-Code 설계 (초안, 2026-11-12)

상태: §8 정책 확정(2026-11-12). **M3.1·M3.2 구현 완료** — §9(설계 차이 2건 사용자 승인). M3.3 이후와 PoC 실행은 아직 하지 않았습니다.

목표: 자연어 요구사항 → 기획 → UX/디자인 명세 → **실제 제품 UI(컴포넌트·페이지) 구현** → 테스트 → 사용자 승인까지 이어지는 범용 워크플로.
M3가 새로 메우는 구간은 "승인된 디자인 산출물 → 제품 코드(UI)"와 "UI 구현 결과의 검증·사용자 검토"입니다. 나머지는 M1·M2 기능을 그대로 씁니다.

### 1.2 Design-to-Code 준비 수준

- **뼈대는 준비됨**: 승인 게이트, 배치 계획, 실행 범위 보호, 테스트 증거, 최종 승인, 정책 원장은 화면 구현에도 그대로 쓸 수 있습니다.
- **UI 고유 연결이 비어 있음**: 디자인 산출물(02 상태·04 CMP·테마)이 제품 코드와 **기계적으로 대조되지 않습니다.** 지금은 Claude가 문서를 읽고 "알아서" 구현하며, 엔진은 AC 테스트 통과만 봅니다.
- 결과적으로 지금도 UI 구현은 가능하지만, 다음은 보장되지 않습니다: 승인 토큰 사용, 공통 컴포넌트 중복 방지, 상태 6종 구현, 브라우저 렌더링, 사람이 화면을 보고 승인.

## 2. 설계 원칙

1. **새 Skill을 만들지 않습니다.** Design-to-Code는 `/product-build`의 UI 배치 실행을 강화하는 것입니다. 디자인 문서는 `/product-design`, 코드는 `/product-build`가 소유하는 현재 경계를 유지합니다.
2. **화면별 새 문서를 만들지 않습니다.** 화면 계획은 승인된 02·04·05·07·테마·구현 계획에서 **스크립트가 파생**하고, Claude가 채우는 부분만 배치 작업 기록(`.ai-workflow/build/`)에 둡니다. 사람이 읽는 문서는 기존 `00-implementation-plan.md`(생성 문서)에 요약만 추가합니다.
3. **엔진은 프레임워크를 모릅니다.** React·Next.js·Vue, UI 라이브러리, CSS 방식, 테스트 도구는 프로젝트 프로필과 대응표에 적습니다. 엔진은 **파일·ID·리포트 형식**만 검사합니다. 스택별 예시는 선택형 어댑터 템플릿으로만 제공합니다.
4. **브라우저·Figma는 선택형 입력/검사기입니다.** 없으면 `not_run`이나 '사용 안 함'으로 정직하게 기록하고, 흐름은 끝까지 갈 수 있어야 합니다(승인 기준에서 무엇이 빠졌는지 표시).
5. **자동 판정과 사람 판정 분리**(v2 원칙 유지): 자동 검사 0건을 시각 승인으로 간주하지 않습니다. 최종 화면 승인은 사람이 합니다.
6. **기존 승인·해시·상태 불변**: M3는 새 필드·새 명령을 **추가**만 합니다. `build.json` 형식 변경은 하위 호환(필드 없음 = 기존 동작)으로 합니다.

## 3. M3 전체 아키텍처

```
/product-start ──▶ docs/planning (PRD·US·FLOW·AC)                       [기존]
/product-design ─▶ docs/design 00–05, 07(VD), theme(design-theme/v1),   [기존]
                   design-preview/ (시각 기준, 승인 해시)
/product-init ───▶ 보일러플레이트(새 프로젝트)                            [기존]
/product-build
   init/scan ────▶ build-profile.toml  + [ui] 절 (스택·부품 경로·토큰 출력·브라우저 어댑터)   [M3.1 확장]
                   docs/build/ui-map.json  (CMP ↔ 코드 부품 ↔ 토큰 대응표, 프로젝트 소유)   [M3.1 신규]
   plan ─────────▶ implementation-plan.json (기존) + 대응표 대조 검사                        [M3.1 확장]
   batch-start ──▶ ui-brief (배치의 화면·상태·행동·입력·권한·CMP·토큰·VD·AC↔상태) 파생      [M3.2 신규]
   execute ──────▶ ui-plan (화면별 컴포넌트 트리·데이터·API·상태 렌더 경로) 기록·검증       [M3.2 신규]
                   코드 구현 (paths.allow/shared, 보호 경로, 테스트 약화 검사)              [기존]
   verify ───────▶ AC 증거 E0–E3 (기존) + 상태 증거 + 토큰 감사 + 브라우저 리포트          [M3.3·M3.4]
   ui-review ────▶ 검토 묶음(주소·스크린샷) → FB 기록 → ①–⑤ 분류 → 수정/문서 제안           [M3.5 신규]
   approve batch ▶ 최종 사용자 승인(기존 명령, UI 배치는 기본 user)                         [기존 + 정책]
   ledger/decide ▶ API 미정 계약·문구 공백·정책                                            [기존]
```

### 3.1 화면별 컴포넌트 트리 — `ui-plan`
- **입력(파생, 스크립트)**: `ui-brief --batch Bxx`가 배치 소유 화면의 02 블록(상태 표·행동·입력·권한별 노출·진입/이탈), 05의 AC→상태, 04의 CMP(용도·변형·상태·접근성), 07의 승인 VD, 테마 토큰 이름, `ui-map.json`의 기존 부품을 한 JSON으로 묶습니다.
- **작성(Claude)**: 화면마다 트리를 `ui-plan`(배치 작업 기록)에 적습니다.
  - 노드: `{ "cmp": "CMP-003" | null, "part": "<코드 부품 이름>", "local": true|false, "props_from": "<데이터 필드>", "children": [...] }`
  - 화면 상태별 렌더 경로: `{ "state": "SCR-001-ST2", "how": "route|query|prop|story", "ref": "..." }`
  - 데이터: 화면이 쓰는 데이터 모양과 출처(API 작업 ID 또는 mock), 상호작용(행동 → 결과 → 상태 전이).
- **검증(스크립트, `ui-plan-validate`)**: 02의 모든 상태(‘해당 없음’ 제외)에 렌더 경로가 있음 / 트리의 CMP가 04에 있고 대응표나 계획 `components.new`에 있음 / 대응표에 있는 CMP를 로컬 부품으로 새로 만들지 않음 / 05에서 상태에 연결된 AC가 배치 `test_plan`에 있음.
- 사용자 승인 대상이 아닙니다(승인된 문서를 따르는 구현 세부). 승인 문서와 다르게 만들어야 하면 원장(편차)으로 보냅니다.

### 3.2 공통 컴포넌트 재사용 판단 — `ui-map.json`
- 프로젝트 소유 파일(`docs/build/ui-map.json`). 엔진은 형식과 대조만 합니다.
  ```json
  { "format": "pb-ui-map/v1",
    "components": { "CMP-001": { "path": "frontend/src/components/Button.tsx", "export": "Button", "source": "existing|built|library", "variants": {"primary": "variant=\"primary\""} } },
    "tokens": { "output": "frontend/src/styles/tokens.css", "format": "css-vars", "var_pattern": "--{dashed}" },
    "library": { "name": "<선택: UI 라이브러리 이름@버전>", "note": "..." } }
  ```
- 판정 순서: ① 대응표에 있는 CMP → 재사용(필수) ② 대응표에 없고 `scan`이 이름·표지로 찾은 후보 → 사용자 확인 후 대응표에 등록 ③ 없음 → 계획 `components.new`(B0 또는 첫 사용 배치)가 만들고 배치 완료 시 대응표에 추가.
- 검사: 대응표 경로 존재, 계획 `components.new`가 이미 대응표에 있으면 오류(`cmp_already_mapped`), 같은 CMP 두 배치 신규(기존 `cmp_new_duplicate`), 배치 완료 시 새 CMP의 대응 누락.

### 3.3 디자인 토큰 및 스타일 매핑 — 토큰 브리지
- 기준: 테마 파일(있으면) + 04 토큰. 계산은 기존 `pd_theme`의 기대값 로직을 재사용합니다(product-build는 이미 pd_core 함수를 읽기 전용으로 가져옴).
- `token-sync --check`: 대응표 `tokens.output`의 값이 기대값과 같은지 비교. `css-vars`는 엔진이 직접 비교하고, 그 밖의 형식(TS 객체, 유틸리티 CSS 설정 등)은 프로젝트의 **내보내기 명령**이 JSON(`{ "토큰 이름": "값" }`)을 출력하게 해 비교합니다(프레임워크를 엔진이 모름).
- `token-audit`: 배치 범위 파일에서 색·간격 직접 값 사용을 찾아 보고(패턴·허용 목록은 프로필). 기본은 경고, 프로필로 차단 가능.
- 토큰 이름이 더 필요하면 코드에서 만들지 않고 `/product-design`의 ② 변경(UX Spec 개정)으로 안내합니다(기존 규칙).

### 3.4 상태 관리와 사용자 인터랙션
- 엔진은 상태 관리 방식을 정하지 않습니다. `ui-plan`의 상호작용 표(행동 → 결과 → 상태 ID)를 02의 행동 표와 대조해 누락만 찾습니다.
- 행동 결과가 02에 없으면 구현하지 않고 원장(정책/편차)에 올립니다(M2.4b 규칙 그대로).

### 3.5 API 계약과 Mock 데이터
- 기존 계획의 `api`·`be` 작업과 `order_strategy`(`mock-first`, `api-first`)를 그대로 씁니다.
- 프로필 `[ui] api_contract`(선택): 계약 파일 경로(OpenAPI, 타입 파일 등). 있으면 `ui-plan`의 데이터 출처가 계약의 항목을 가리키는지 확인합니다.
- Mock은 **제품 코드 범위 안**(`paths.allow`)에 두고 `ui-plan`에 `mock: true`로 표시합니다. Mock으로 검증한 AC는 증거에 `mock` 표시가 붙고, 실제 API 연결 배치가 끝나면 재검증 대상이 됩니다(기존 `impact`·stale 메커니즘).
- 계약이 정해지지 않은 외부 계약은 원장의 차단 정책(외부 계약)으로 등록합니다.
- `design-preview/src/mock/`은 제품 코드에서 import하지 않습니다(기존 보호 경로).

### 3.6 로딩·빈 화면·오류 상태
- 02의 상태 6행이 기준입니다. `SCR-xxx-STn` 태그를 **상태 증거**로 인정합니다(AC 태그와 같은 규칙: `[SCR-001-ST2] …`).
- 판정: 상태별 E0/E1/E2. 목표는 프로필(권장 기본: Must 화면의 정의된 상태는 E2, 나머지는 경고).

### 3.7 반응형 레이아웃
- 02의 `플랫폼`(mobile·responsive·공통)과 04 `breakpoint.*` 토큰, 프로필 `browser.viewports`(기존 필드)를 씁니다. 화면별 검사 뷰포트 = 플랫폼에 맞는 프로필 뷰포트.
- 판정은 브라우저 리포트의 `overflow`(가로 넘침)·`clipped`(가림)·`touch_target` 결과로 합니다. 수치 기준은 프로필 값이며 엔진 기본값은 없습니다.

### 3.8 접근성
- 04 CMP의 `접근성` 필드와 `review-checklist.md`(기존)를 구현 기준으로 씁니다.
- 자동: 브라우저 리포트의 접근성 위반(도구는 어댑터가 선택. 심각도별 개수), 대비는 테마 값으로 계산(WF-D10 일부를 `token-sync`에 포함 검토).
- 수동: 키보드·스크린리더 확인은 EM(수동 증거)으로 기록합니다.

### 3.9 화면별 AC와 테스트 연결
- 기존 AC 태그·증거 수준을 그대로 씁니다. 추가는 상태 증거(§3.6)와 브라우저 리포트의 `acs` 필드(브라우저 시나리오가 AC를 검증하면 E2 근거)뿐입니다.
- 05의 AC→상태 연결로 "AC는 통과했지만 그 상태 화면은 렌더링 안 됨" 같은 불일치를 보고합니다.

### 3.10 구현 결과의 브라우저 검증
- 엔진이 정하는 것: 리포트 형식 `pb-ui-report/v1`과 판정 규칙.
  ```json
  { "format": "pb-ui-report/v1", "tool": "<도구@버전>", "base_url": "...",
    "results": [ { "screen": "SCR-001", "state": "SCR-001-ST1", "viewport": "mobile",
                   "rendered": true, "console_errors": 0, "a11y": {"critical": 0, "serious": 1},
                   "overflow": false, "touch_target_violations": 0, "acs": ["AC-001"],
                   "interactions": [ {"name": "좌석 선택", "passed": true} ],
                   "screenshot": "<PB_REPORT_DIR 안 상대 경로>" } ] }
  ```
- 프로젝트가 정하는 것: 실행 명령(프로필 `verify.steps`의 `stage = "browser"`, 기존 구조), 앱 기동 방법, 도구. 엔진은 Playwright 등을 설치·호출하지 않습니다. Skill 템플릿에 **선택형 어댑터 예시**(예: React+Vite+Playwright 1종)를 둡니다.
- 판정(제안): 렌더 실패·콘솔 오류·접근성 critical·상호작용 실패 = 실패, 그 밖은 보고. 도구가 없으면 `not_run` → 해당 항목은 증거 없음으로 남고 최종 승인 화면에 표시.
- 스크린샷은 `.ai-workflow/build/evidence/`(이미 Git 제외)에 보관하고 요약만 `build.json`에.

### 3.11 사용자 승인 및 수정 요청 — `ui-review`
- `ui-review --batch Bxx`(verified 이후): 화면·상태·뷰포트별 스크린샷 목록, 로컬 실행 주소, AC·상태 증거 요약, `not_run` 항목, 프리뷰(L3)와의 대비 링크를 한 묶음으로 보여 줍니다.
- 피드백 → `ui-feedback add`로 FB 기록 → 분류는 `/product-design`의 ①–⑤ 규칙을 재사용(엔진 함수 재사용, 디자인 상태는 변경하지 않음):
  - ④ 시각 표현·⑤ 구현 메모 → 이 배치에서 수정(`resume --batch`) → 재검증
  - ③ 테마 값 → `/product-design` 테마 변경 안내(토큰 브리지 재동기)
  - ①·② 정보·행동·토큰 의미 → 코드로 바꾸지 않고 문서 반영 제안(기존 doc-proposal) + 소유 Skill 재검토
- 최종 승인은 기존 `approve batch --note`(사용자 원문). UI 배치의 기본 승인 정책을 `user`로 할지(§8 결정 1).

  - AC 3–4개(빈 좌석 표시, 사용 중 좌석 선택 불가, 확정 후 상태 반영, 불러오기 실패 시 재시도)
- **성공 조건 대응**

| PoC 조건 | 확인 방법 |
|---|---|
| 1. 승인 문서 → 구현 계획 | `scope --draft` → 계획 승인(B0 foundation + B1 SCR-001), `ui-brief`/`ui-plan-validate` 통과 |

- **신규**: 상태 태그 규칙, 상태 증거 요약, EM 기록.
- **의존성**: M3.2(상태 목록).

### M3.4 브라우저 검증 리포트

- **신규**: 리포트 형식·판정, 어댑터 예시(엔진 코드 밖 템플릿).
- **의존성**: M3.3.
- **테스트·완료 기준**: 가짜 리포트로 실패·통과·미실행 판정(엔진 테스트는 브라우저 없이), 실제 브라우저 1회는 PoC에서. 도구 없는 환경에서 흐름 완료(`not_run` 표시).
- **위험**: 앱 기동·포트·시간 초과(→ 프로필 명령에 위임, 기존 timeout), 스크린샷 용량.
- **사용자 승인 지점**: 브라우저 도구 설치는 사용자 확인(위험 변경).

### M3.5 UI 검토·수정 요청 루프

## 9. 확정 정책과 M3.1·M3.2 구현 기록 (2026-11-12)

### 9.2 구현(설계 대비 차이 포함)
- 모듈 `skills/product-build/scripts/pb_ui.py`, 명령 `ui-map`·`token-check`·`token-audit`·`ui-brief`·`ui-plan-validate`, 문서 `reference/ui.md`.
- 토큰 출력 설정은 프로필이 아니라 **대응표(`docs/build/ui-map.json`)**에 둡니다. 프로필은 계획 승인 해시 대상이라, 실행 중 토큰 파일 지정·예외 추가가 계획을 무효로 만들지 않게 하기 위함입니다. 프로필 `[ui]`에는 검사 범위·방식(감사 모드·종류·확장자, 계약 파일)만 둡니다.
- 프로젝트 허용 예외(토큰·직접 값)는 사유 + 사용자 문장이 있어야 등록됩니다.
- UI Brief는 **승인된 계획**의 배치에만 만듭니다(설계의 'batch-start 시 파생'보다 앞당김: 실행 전 검토 가능). 계획·입력이 바뀌면 `plan_modified`·`plan_outdated`로 거부합니다.
- 계획 검증의 대응표 대조(`cmp_already_mapped`)는 **대응표가 있을 때만** 동작합니다(M2 프로젝트 동작 불변).
- 테스트: `tests/product_build_ui_test.py`(독립 픽스처: 기존 프로젝트 A / 신규·v2 테마·DD 프로젝트 B).
- 사용자 승인(2026-11-12): 위 차이 중 ① 토큰 출력·허용 예외를 `ui-map.json`에서 관리, ② UI Brief를 계획 승인 직후부터 생성 — 두 가지를 승인. 조건: 토큰 예외가 추가·변경·삭제되면 관련 검증 결과를 무효화하고 다시 검사하며, 예외 사유와 사용자 확인 기록을 유지합니다(M3.3·M3.4 작업에서 적용).
