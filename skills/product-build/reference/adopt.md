# 기존 구현 adopt와 증거 수준

이미 코드가 있는 프로젝트(예: 엔진 밖에서 먼저 구현한 경우)에서 기존 코드·테스트·라우트를 계획의 화면·AC·배치와 연결할 **후보**를 만듭니다. M2.1은 **분석만** 합니다. `build.json`이나 승인·검증 이력을 만들지 않습니다(`--save`는 분석 결과 파일 `.ai-workflow/build/adopt-analysis.json`만 씀).

## 1. 무엇을 보는가

| 신호 | 방법 | 의미 |
|---|---|---|
| 라우트 | IA·화면 명세의 경로를 정적 구간 그대로, 매개변수 구간(`:id`)은 아무 식별자로 바꿔 소스 문자열에서 찾음 | 라우트 정의·링크가 **있을 수 있음** |
| ID 언급 | 소스·테스트의 `SCR/US/AC/FR/CMP/UXD/VD-xxx`(범위 표기 `AC-024–033` 포함) | 개발자가 이 ID를 **언급함** |
| 컴포넌트 | 프로필 `paths.components`의 파일 → `CMP-xxx` 표지 또는 이름 일치, import 사용처 수 | 04 컴포넌트와 대응하는 **후보** 파일 |

## 2. 화면 신호(`signal`)

| 값 | 조건 | 후보 여부 |
|---|---|---|
| `route_and_id` | 라우트 + ID 언급 | 후보 |
| `route_only` | 라우트만 | 후보 |
| `parent_route_and_id` | 시트·패널 화면: 부모 경로 + ID 언급 | 후보 |
| `parent_route` | 시트·패널 화면: 부모 경로만 | 아님 |
| `id_only` | ID 언급만 | 아님(주석일 수 있음) |
| `placeholder` | 경로·ID가 나오는 코드 줄이 모두 자리표시자(`pending`, `placeholder`, `TODO`, `stub`, `준비 중`, `미구현` 등; 프로필 `[adopt] placeholder_words`로 추가) | 아님(아직 구현 안 된 자리) |
| `none` | 신호 없음 | 아님 |

**배치 후보**
- `existing_candidate`: 화면의 절반 이상이 후보
- `partial_candidate`: 일부만 후보
- `no_signal`: 신호 없음(신규 구현 대상)

## 3. AC 증거 수준 — 언급과 검증의 구분

| 수준 | 기준 | 누가 판정 |
|---|---|---|
| E0 | 테스트에 언급 없음 | adopt(M2.1) |
| **E1 언급** | 테스트 파일 이름·제목·주석에 AC ID가 나옴. **검증으로 세지 않음** | adopt(M2.1) |
| E2 연결·실행 | 구조화된 태그가 붙은 테스트가 **증거 실행의 테스트 리포트(JUnit XML·러너 JSON)에서 통과**로 확인됨 | M2.3 |
| E3 검증 | E2 + Then 항목별 assertion 대응표 + 구현 전 실패 → 구현 후 통과 기록(사후 등록은 대응표 검토로 대신하고 E3*로 표시) | M2.3 |
| EM 수동 | 자동화할 수 없는 이유 + 근거(스크린샷 등) + 사람 확인 | M2.3 |

- adopt는 E0·E1만 매깁니다. 모든 항목에 `verified: false`가 붙습니다.
- 보고할 때는 "N개 AC가 테스트에 언급됨(E1)"처럼 쓰고, "검증됨"이라고 쓰지 않습니다.

## 4. 이후 단계(M2.2·M2.3)

1. 사용자 확인 후 후보 배치를 `imported` 상태로 등록합니다. 승인 이력은 없습니다.
2. 프로필의 검증 명령과 테스트 리포트로 E2 이상을 판정합니다.
3. 부족한 AC는 테스트를 보강합니다.
4. 그다음 일반 배치처럼 승인합니다.
